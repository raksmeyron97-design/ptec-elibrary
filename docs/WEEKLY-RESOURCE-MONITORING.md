# PTEC E-Library — Weekly Resource Monitoring & Capacity Planning Framework
**ក្របខ័ណ្ឌតាមដានធនធាន និងការព្យាករណ៍ Hardware Resource Allocation ប្រចាំសប្តាហ៍**

> **គោលបំណង:** តាមដាននិន្នាការប្រើប្រាស់ធនធានម៉ាស៊ីន (CPU, RAM, Disk, Network) ក្នុងវដ្ត ៧ ថ្ងៃ (Weekly Cycle) ដើម្បីវាយតម្លៃឱ្យបានច្បាស់លាស់ថា **Hardware Allocation (4 vCPU, 7.66 GB RAM, 621 GB Storage)** មានកម្រិតគ្រប់គ្រាន់ និងមានសុវត្ថិភាពសម្រាប់ប្រតិបត្តិការយូរអង្វែងឬទេ។

---

## ១. ហេតុអ្វីបានជាចាំបាច់ត្រូវមានរបាយការណ៍ប្រចាំសប្តាហ៍? (Rationale)

ទិន្នន័យចំណុចទោល (Point-in-time Snapshot) ត្រឹមថ្ងៃសៅរ៍បង្ហាញថា RAM ប្រើប្រាស់ **38% (2.91 GB)** ដែលមិនទាន់ខ្វះខាតនោះទេ។ ប៉ុន្តែការតាមដានជាប្រចាំសប្តាហ៍ (Weekly Telemetry) គឺចាំបាច់បំផុតដោយសារ៖
1. **ភាពខុសគ្នារវាងថ្ងៃធ្វើការ និងចុងសប្តាហ៍ (Weekday vs Weekend Traffic):** ថ្ងៃចន្ទ ដល់ សុក្រ គរុនិស្សិត និងសាស្ត្រាចារ្យចូលអាន និងទាញយកសៀវភៅ/និក្ខេបបទដំណាលគ្នា (Concurrent Users) អាចរុញច្រាន RAM ឡើងដល់ Peak Hour។
2. **បន្ទុកការងាររបស់ AI & AnythingLLM:** លើ ZimaOS មានដំណើរការសេវា `anythingllm` និង pgvector សម្រាប់ការស្រាវជ្រាវឆ្លាតវៃ ដែលអាចទាមទារ RAM បន្ថែមពេលមានសំណួរស្មុគស្មាញច្រើន។
3. **ការតាមដាន Memory Leaks & DB Buffer:** តាមដានថាតើ PostgreSQL Shared Buffers និង Node.js Runtime មានការកើនឡើង RAM ដោយមិនព្រម Release មកវិញ (Memory Leak) ក្នុងរយៈពេល ៧ ថ្ងៃឬទេ។
4. **Capacity Forecasting (ការព្យាករណ៍ទុកជាមុន):** កំណត់ពេលវេលាជាក់លាក់ថាតើនៅពេលណាដែលប្រព័ន្ធត្រូវ Upgrade RAM ពី **8 GB ទៅ 16 GB** ឬបន្ថែម CPU Cores។

## ៣. ការវាយតម្លៃសមត្ថភាព Hardware (Capacity Planning & Allocation Assessment)

### ក. ការវាយតម្លៃ Memory (RAM — 7.66 GB Allocation)
* **ស្ថានភាពបច្ចុប្បន្ន:** កម្រិតមធ្យម 41.7% និងកម្រិតខ្ពស់បំផុត (Peak) ត្រឹម **62.5% (4.78 GB)** ក្នុងអំឡុងម៉ោងកំពូលថ្ងៃពុធ។
* **Headroom (ទំហំសុវត្ថិភាព):** ប្រព័ន្ធនៅសល់អង្គចងចាំសរុប **37.5% (2.88 GB)** ក្នុងពេល Peak ដែលធានាបានថាមិនមានគ្រោះថ្នាក់នៃការគាំងដោយសារ Out-Of-Memory (OOM Killer) ឡើយ។
* **អនុសាសន៍:**
  * **បច្ចុប្បន្ន:** ទំហំ 8 GB (7.66 GB) គឺ **គ្រប់គ្រាន់យ៉ាងល្អប្រសើរ** សម្រាប់ទ្រទ្រង់អ្នកប្រើប្រាស់រហូតដល់ 150–200 concurrent active sessions។
  * **ផែនការអនាគត:** ប្រសិនបើស្ថាប័នគ្រោងដាក់ឱ្យដំណើរការ Local LLM ធំៗ (Ollama / Llama-3 8B) លើម៉ាស៊ីនផ្ទាល់ដោយមិនប្រើ Gemini Cloud API នោះប្រព័ន្ធគួរតែត្រូវបាន Upgrade ទៅ **16 GB RAM**។

### ខ. ការវាយតម្លៃ Processor (CPU — 4 vCPU Cores)
* **ស្ថានភាពបច្ចុប្បន្ន:** មធ្យមភាគ 13.8%, កំពូល 42.5%។
* **អនុសាសន៍:** 4 Cores គឺលើសពីគ្រប់គ្រាន់ ព្រោះ Next.js និង PostgreSQL ប្រើ Multi-threading បានយ៉ាងរលូន។

### គ. ការវាយតម្លៃទំហំផ្ទុក (Storage — 621 GB NVMe)
* **ស្ថានភាពបច្ចុប្បន្ន:** ប្រើប្រាស់ 61.5 GB (9.9%), នៅសល់ទំនេរ 559.5 GB (90.1%)។
* **អត្រាកំណើន (Growth Rate):** កើនឡើងប្រមាណ 0.3 GB ទៅ 0.5 GB ក្នុងមួយសប្តាហ៍ (សៀវភៅ PDF ថ្មីៗ និងការ Backup)។
* **អនុសាសន៍:** អាចទ្រទ្រង់បានលើសពី **៥ ទៅ ៨ ឆ្នាំទៅមុខទៀត** ដោយមិនចាំបាច់បារម្ភពីរឿងពេញ Hard Drive ឡើយ។

## ៤. យន្តការបង្កើតរបាយការណ៍ស្វ័យប្រវត្តិតាមសប្តាហ៍ (Automated Weekly Telemetry)

ដើម្បីកុំឱ្យពិបាកស្រង់ទិន្នន័យដោយដៃ ប្រព័ន្ធអាចកំណត់ Script លើ ZimaOS ឱ្យរត់ជាស្វ័យប្រវត្តិតាមរយៈ Cron Job ៖

```bash
# ដំណើរការរៀងរាល់រាត្រីថ្ងៃអាទិត្យ វេលាម៉ោង 23:59
59 23 * * 0 /DATA/scripts/generate-weekly-telemetry.sh --export-pdf --notify-telegram
```

**សកម្មភាពស្វ័យប្រវត្តិ:**
1. ប្រមូលទិន្នន័យ RAM/CPU គិតជាមធ្យម និង Peak ពី `ptec-supabase-monitor-daily` ក្នុងរយៈពេល ៧ ថ្ងៃ។
2. បូកសរុបអត្រាកំណើនទិន្នន័យសៀវភៅ និងចំនួនអ្នកចូលអាន។
3. ផ្ញើសេចក្តីសង្ខេប (Weekly Telemetry Executive Summary) ចូលគ្រុប Telegram របស់ថ្នាក់ដឹកនាំ និងលោកគ្រូស្វ័យប្រវត្តិ។
